## 第 0 步：先搞懂"视频压缩"到底在干什么

你想一个问题：一段 10 秒钟、1920x1080 的视频，如果一帧一帧原样存下来（不压缩），要多大？

- 一帧 = 1080 行 × 1920 列 ≈ 200 万个像素
- 每秒 25 帧，10 秒 = 250 帧
- 每个像素要 1.5 个字节（YUV420 格式）
- 算下来大约 **8 个 GB**

8 个 GB 才存 10 秒！这谁受得了。所以必须压缩。

压缩靠的不是魔法，而是两个朴素的事实：

1. **同一张图里，相邻的地方长得像**。比如一片天空，左边和右边几乎一样蓝。
2. **相邻两帧之间，大部分地方根本没变**。比如一个静止的摄像头，画面里只有一个人在走动，背景 99% 都没动。

视频压缩就是抓住这两点，尽量**少记东西**。这就是后面所有知识的总纲。

# PDF 一：H.265 是个什么样的东西，它的码流长什么样

## 1.1 H.264 和 H.265 的区别

你可以把 H.264 想成"旧款省油车"，H.265 是"新款更省油的车"。

**它俩是干同一件事的**：把视频压小。区别就是 H.265 压得更狠：

- 同样的画质，H.265 压出来的文件大约只有 H.264 的 **60% 左右**（也就是省了约 40%）。
- 代价是：**H.265 编码的时候电脑要算得更多**。就像新款车更省油，但发动机更复杂、更贵。

**为什么能压得更狠？** 靠的是下面这几招改进。

### 招数 1：把画面切块切得更聪明

先解释一个关键概念：**编码单位（块）**。

视频压缩不是整张图一起处理的，而是把画面**切成一块一块的小格子**，一块一块地单独处理。就像你在记账本上，把一张大白纸分成很多小方格，每个格子里单独写"这一格该怎么记"。

- **H.264 的做法**：每块**固定是 16x16** 这么大。不管画面是平坦还是复杂，都是这个尺寸。就像用一把固定尺寸的尺子切蛋糕，不管蛋糕多大都切成一样大的块。
- **H.265 的做法**：块可以**从 8x8 到 64x64 随便选**。画面平的地方（比如一片蓝天）用 64x64 的大块——反正都一个颜色，一个大块记一笔就够了，省；画面复杂的地方（比如草地、轮胎）切成 8x8 的小块——因为这里每小块都不一样，切小了才能记准。

你可以这么想：**H.264 是"一刀切"，H.265 是"看菜下饭"**。这就是 H.265 省码率的最大原因之一。

H.265 里块还有个新说法，叫 **CTU/CU/PU/TU**，其实就是三层不同职责的"格子"：
- CU（编码单位）：负责"我这一块要不要拆小"——管分块；
- PU（预测单位）：负责"这块用哪种方式去猜"——管预测；
- TU（变换单位）：负责"这块的误差怎么打包"——管打包。

不用背，你只要知道：**H.265 把"分块、预测、打包"这三件事拆开各管各的，所以更灵活**。

### 招数 2：帧内预测——"用邻居猜自己"

一句话：**同一张图里，用旁边已经算好的像素，去猜当前的像素**。

比方：一幅图上有一面墙，你只知道左边几列的墙是"浅黄色"，那右边这列的墙八成也是浅黄色，不用重新存，直接说"照着左边来"就行。这比把每一列的颜色都写下来省多了。

H.264 提供了 8 个"猜测方向"（只能横着猜、竖着猜、斜着猜几种）；H.265 提供了 **33 个方向**，还多了两种特殊猜法（DC：取平均，Planar：画个渐变）。方向越多，猜得越准，要补的"误差"就越小，码率就越低。

### 招数 3：帧间预测 + 运动矢量——"用前一帧猜这一帧"

这个更重要，是视频压缩的大头。

**概念一：I 帧 / P 帧 / B 帧**

- **I 帧（关键帧）**：一张**完整**的照片，不靠任何其他帧，自己就能存下来。每隔一段（比如 1~2 秒）来一张，作为"参考点"。
- **P 帧**：只记**"变化的部分"**。比如镜头里一辆车往右开，P 帧不重新画车，只记一句"车往右挪了 3 个像素"。
- **B 帧**：比 P 帧更贼，**"前后两帧结合着猜"**。就像你想猜中间那帧，可以先看看前帧和后帧，取个中间值。

**概念二：运动矢量（MV）**

"车往右挪了 3 个像素"里的"右挪 3 个像素"就是运动矢量。H.265 的运动矢量范围比 H.264 大得多，能描述更大幅度的运动（高清视频里物体动得远）。

**概念三：猜完要补差（残差）**

猜不可能 100% 准。比如车挪了 3 个像素，但挪完发现其实和真实画面还差一点点（多了一点阴影）。这个"差的部分"叫**残差**，也必须存下来，但残差通常很小，存起来很便宜。

所以帧间压缩的本质是：**猜（预测）+ 只记猜错的部分（残差）**。猜得越准，残差越小，文件越小。

H.265 还提供了更聪明的"抄作业"方式叫 **merge 模式**：这一块的运动直接**照抄隔壁那块的运动**（因为一个物体往往是一大片一起动的），连猜都不用猜，直接继承，特别省。H.264 也有类似的东西，但 H.265 的候选更多、更智能。

### 招数 4：把"误差"做一次"舍得"——变换和量化

这一招藏在压缩链路中间，稍微抽象，我用一个比喻：

猜完画完，还剩下"残差"（那些细微的差）。这个残差怎么存？直接存原始数字很费。H.265 的做法是把残差**拆成"大块的轮廓 + 小块的细节"**，然后**把小细节里不太重要的扔掉**。

这就是"变换（把误差拆成不同粗细的成分）"和"量化（把细微成分粗糙化，甚至归零）"。

量化是**压缩有损**的核心来源：你扔掉了一点人眼几乎看不出来的细节，换来了文件大幅变小。量化参数 QP 就是这个"舍得程度"的旋钮：**QP 越小 = 保留越多 = 画质好文件大；QP 越大 = 扔得越多 = 画质差文件小**。

### 招数 5：熵编码——"最后再压一遍水"

残差算完、量化完，剩下一堆"0 和 1 的数据流"。熵编码就是**把这段数据再打包压一遍**，尽量让"很常见的情况用很短的记号"。

H.265 用的熵编码叫 **CABAC**。它有点像摩斯密码：字母"e"出现最多，就用最短的符号（一个点）；"z"很少见，用长一点的符号。CABAC 更聪明，它会**根据已经出现过的内容实时调整概率**，从而压得更狠。

H.264 时代有两个选择：CABAC（压得好但费算力）和 CAVLC（压得差但省算力）。**H.265 直接砍掉 CAVLC，只留 CABAC**，因为现代硬件算力够用，干脆都用好的。

### 招数 6：去块滤波——"把格子的接缝磨平"

还记得画面被切成一格一格的吗？一格一格单独处理，格子**边缘就会出现"接缝"**（像拼图拼得不太齐），看起来有马赛克感。

**去块滤波（DBF）** 就是一道"磨平工序"：把格子边界的像素稍微平均一下，让接缝消失。就像你拼完拼图，拿手把接缝处抹一抹。

H.265 对这道工序做了优化：只对 8x8 的边界做（H.264 是 4x4），而且**先整幅图处理竖的边，再整幅图处理横的边**。这么改的好处是：**可以多线程并行**（多个 CPU 核同时磨不同区域），处理更快。

### 招数 7：SAO 滤波——"补一点颜色修正"

去块滤波之后，H.265 还有一道独门工序叫 **SAO（样本自适应偏移）**。作用是给某些像素**补一点亮度修正**，用来对付"颜色分层（一条条色带）"和"边缘发毛（振铃）"这些瑕疵。比如大色块渐变的地方容易出现一圈圈的色带，SAO 能给它抹匀一点。

## 1.2 H.265 的分层结构和码流（NALU）

### 视频文件在硬盘上到底是怎么排的？

H.265 的"裸码流"（就是那个 `.h265` 文件）内容其实很简单：**就是一串一节一节的数据，每节前面有个分隔标记**。

就像一辆火车，**一节车厢**是一个 NALU，**车厢之间的挂钩**是"开始码"。

### 一个 NALU 长什么样？（重点）

一个 NALU = **开始码 + 头部 + 数据** 三部分，我拆开讲：

**① 开始码（Start Code）**：就是 `00 00 01` 或 `00 00 00 01` 这么几个字节，作用是告诉解码器"注意！下一节 NALU 开始了"。它就是车厢之间的挂钩/胶带。

**② NALU 头部（Header，2 个字节）**：这就是"快递单"，上面写着这个包裹里装的是什么东西。这一小块是本次讲解的重中之重，我详细说：

头部一共 16 个 bit（2 字节），分成 4 段：

- **F 位（1 bit）**：紧急标志。0 = 正常，1 = 网络传输中出了错。一般永远是 0。
- **类型（6 bit）**：**最关键**。告诉你这个包裹里装的是"参数说明书"还是"图像数据"还是"辅助信息"。怎么读出来呢？公式是：
  ```
  类型 = (第一个字节 & 0x7E) >> 1
  ```
  也就是把第一个字节的第 2~7 位抠出来。**你不用会算，你只要知道：拿到第一个字节，用这个公式一算，就知道是什么类型了**。
- **层 ID（6 bit）**：用来做多视点、多图层（比如 3D、画中画）的，普通视频这里全是 0。
- **时间层（3 bit）**：时域分层用的，普通视频这里是 1。

**③ NALU 数据（Payload）**：真正的内容。包括参数、图像数据等等，后面讲。

### 常见的 NALU 类型有哪些？（必背）

- **VPS（类型 32）**：整个视频的"总说明书"。
- **SPS（类型 33）**："一批视频"的说明书。
- **PPS（类型 34）**："单张图"的说明书。
- **SEI（类型 39）**：辅助信息，比如字幕、时间戳，删了也不影响解码。
- **IDR（类型 19/20）**：完整的关键帧（I 帧）。
- **CRA（类型 21）**：另一种关键帧。
- 类型 0、1 等：普通帧（P 帧/B 帧）。

一个正常的 H.265 码流开头，通常长这样：

```
开始码 | VPS | 开始码 | SPS | 开始码 | PPS | 开始码 | SEI | 开始码 | IDR | 开始码 | P帧 | 开始码 | B帧 | ...
```

也就是说，**每个"说明书"和"图像数据"都被开始码分隔开，一节能一节**。解码器的工作就是：碰到开始码 → 读 2 字节头部 → 看类型 → 按类型处理。就这么简单。

### 一个小坑：如果数据里恰好出现了"开始码"的样子怎么办？

你可能会想到一个问题：万一图像数据里正好出现了 `00 00 01` 这几个字节，解码器会不会误以为这是一个新 NALU 的开始？

会！所以编码器用了一个"防撞车"机制，叫**防竞争字节**：

- 规则：数据里如果出现了 **两个连续的 `00`，而且下一个要写的字节又是 00、01、02、03 之一**（都很小），就在中间**偷偷插一个 `03`**。
- 解码器看到 `00 00 03`，就知道这个 `03` 是假的，把它删掉，恢复原样。

打个比方：怕快递单号码被误认，就在某些号码中间插一个"分隔符"，收到货再撕掉。**记住"看到 00 00 03 就把 03 删掉"** 这一句就够了。

## 1.3 三份说明书：VPS、SPS、PPS

为什么要有"说明书"？因为解码器光有图像数据，**不知道画面是多大、是什么颜色格式、怎么拆块**，它没法解。所以编码器必须先发几份"说明书"给解码器。

用比喻：你网购了一件组装家具。
- **VPS（总说明书）**：讲清楚"这个产品有几层、几件套"——描述整个视频的框架。它是 H.265 **新增**的，H.264 没有。
- **SPS（批次说明书）**：讲清楚"这批家具每件的尺寸多大、什么材质"——描述分辨率、位深、颜色格式等**一整段视频**通用的参数。
- **PPS（单件说明书）**：讲清楚"这一件怎么组装"——描述**某一幅图像**的专属参数，比如压缩得多狠（QP 初始值）、去块滤波开不开。

顺序是：VPS → SPS → PPS，一层套一层，就像：**产品目录 → 批次规格 → 单件图纸**。

**PDF 里那一大堆英文语法元素（vps_max_layers_minus1 之类），你不用逐个记，你只需要知道它们在回答哪几个问题：**

- **这视频能分几层？**（`*_max_layers_minus1`、`*_max_sub_layers_minus1`）
- **分辨率多大？颜色格式是 4:2:0 还是 4:4:4？每个颜色用几个 bit（8 还是 10）？**（`pic_width`、`chroma_format_idc`、`bit_depth_*`）
- **最多能存几帧参考画面？**（`*_max_dec_pic_buffering`）
- **最多能乱序几帧？**（`*_max_num_reorder_pics`，这个和 B 帧有关）
- **压缩时 QP 从多少开始？**（`init_qp_minus26`）
- **去块滤波开不开、SAO 开不开、能不能多线程并行？**（一堆 `*_enabled_flag`）

看到一份说明书里出现这些词，你知道它"在回答上面某一类问题"就够了。真正写代码时，这些字段都是解码器库（libavcodec）帮你读的，**你基本不用手动解析**，只有当你自己要写一个"裸流解析器"（比如从码流里提取 SPS 拿分辨率）时才需要碰。

## 1.4 档次（Profile）、层（Tier）、级别（Level）——"套餐"和"规格"

这是三个词，用大白话讲：

- **Profile（档次）= 能用的功能套餐**。好比手机套餐：普通套餐（Main，8bit 颜色）、高级套餐（Main 10，10bit 颜色，颜色过渡更平滑，看电视/视频现在基本都用它）。解码器支持高级套餐，就**必须**也能解低级套餐（向下兼容）。
- **Tier（层）= 码率上限的档位**。分"普通档"和"高配档"，高配档允许更高码率（一般 4K/8K 高码率场景用）。
- **Level（级别）= 尺寸上限**。规定最大能解多大分辨率、每秒多少帧。比如某个 Level 能解 1080p，再高的 Level 能解 4K、8K。

一句话：**Profile 管"工具够不够用"，Tier/Level 管"能不能扛得住大活儿"**。

## 1.5 各种 I 帧的区别（类型 19、20、21）——重点中的重点

### 先讲一个背景：视频怎么才能"从中间开始播"？

看视频时你经常拖动进度条（seek），对吧？那问题来了：**视频中间随便一帧，能不能直接开始解？**

不能！因为中间那些帧（P 帧、B 帧）是**靠前后帧猜出来的**，你从中间开始看，前面没看过，它就解不出来。所以视频里必须**每隔一段就放一个"自己就能解"的关键帧**，这种关键帧叫 **IRAP（随机接入点）**。解码器只认这些点：只有拖到 IRAP 上，才能从这里开始解码播放。

### 那 I 帧有哪几种？（19、20、21）

- **类型 20（IDR_N_LP）**：最干净的关键帧。它后面**不允许**有任何"需要它自己解不出来的帧"。它一出现，所有参考画面全部作废，从零开始。解码器看到它最省心。
- **类型 19（IDR_W_DLP）**：同样是关键帧，但允许它后面跟着一小段"特殊帧"（叫 RADL，下面讲）。这几种里面，**19 和 20 都是"完整、安全"的关键帧**，播放器从它开始解码一定没问题。
- **类型 21（CRA）**：这个最坑。它**也是关键帧**（这一帧自己能解），但它所在的这一段（叫 GOP）是**开放式**的——它**后面的某些帧会"翻墙"去参考它前面那个 GOP 的画面**。

### 为什么要搞出 CRA 这种麻烦东西？

因为它**压缩效率更高**。你想想：本来每一段都必须以"完整关键帧"开头，不能参考前一段。但如果允许"参考前一段"，那这一段开头那几帧就不必存成完整画面，可以存成"参考前一段的差"，文件更小。

代价就是：**如果你正好从 CRA 这一帧开始拖进度条，它后面那些"翻墙参考"的帧就解不出来了**（因为前面的参考画面你没收到）。

### 于是又冒出两个新词：RADL 和 RASL

先解释"前置图（leading picture）"：有一些帧，**显示顺序在关键帧之前，但解码顺序在关键帧之后**。听起来绕，其实就是"关键帧后面跟着的那几帧，但播出时排在关键帧前面"（B 帧重排造成的）。

- **RADL**：这种前置图是"幸运儿"，**即使从关键帧开始接，它也能正常解出来**（因为它参考的是关键帧自己）。
- **RASL**：这种前置图是"倒霉蛋"，**它参考了更早的画面，从关键帧开始接就解不出来，必须直接丢掉**。

### 回到你的问题："I 帧 19、20、21 有什么区别？"

- **19**：关键帧，可以带 RADL 前置图。
- **20**：关键帧，**啥前置图都不带**，最干净。
- **21**：CRA，开放式 GOP 的关键帧，压缩率最高，但后面可能跟着解不出来的 RASL 帧。

### 为什么要关心这个？（重要实战结论）

**某些软编码器（比如 libx265）默认会输出类型 21 的 CRA 帧**（因为它默认开了 open-gop，开放 GOP），省码率。但问题是：**有些播放器/硬件解码器/某些 Android 机型不认 CRA 这种"开放式关键帧"**，一遇到就花屏、卡住、没法播放。

所以实战经验是：**如果你编码 H.265 是用来给别人播放的，最好把 open-gop 关掉，强制用 19/20 这种安全的关键帧**。在 FFmpeg 里就是给 libx265 传 `-x265-params open-gop=0`。

# PDF 二：用 FFmpeg 编 H.265 时要注意什么（实战）

这份笔记主要讲你写代码调 libx265 编 H.265 时的几个坑：

**坑 1：分辨率要对**。你喂给编码器的画面宽高（YUV_WIDTH/YUV_HEIGHT）必须和 `frame->width/height` 一致，不然编码器要么报错要么花屏。

**坑 2：时间基准（time_base）要对**。时间戳（PTS）是"视频的时间轴刻度"。如果视频 25 帧/秒，那么 time_base 一般设成 `1/25`，也就是"每一格是 1/25 秒"。设错了，视频可能"快进"或"慢放"，码率计算也会乱。

**坑 3：时间戳要连续**。喂给编码器的每一帧，PTS 必须按顺序连续递增（0、1、2、3…）。因为编码器要重排（B 帧会乱序），如果你喂的 PTS 乱跳，出来的视频时间戳就乱了。

**坑 4（重点）：有些参数 AVCodecContext 设置不生效，要走"x265 专属通道"**。libx265 有很多自己的参数（比如开不开 B 帧、GOP 多长、开不开 open-gop），这些不是 FFmpeg 通用参数，得用特殊方式传：

```cpp
av_opt_set(enc_ctx->priv_data, "x265-params",
           "keyint=250:bframes=3:open-gop=0", 0);
```

格式是冒号分隔、`key=value`，**写错了它会静默失败（不报错但不生效）**，很难排查。

**坑 5（就是上一节讲的）**：I 帧 19/20/21 的区别，上面已经讲透了。

# PDF 三：NVIDIA 硬件编码 H.264（含 NVENC）

## 3.1 软编 vs 硬编，一句话

- **软编**：用 CPU 干活。好处是**质量最好、最灵活**（能用的算法最多）；坏处是**费 CPU、慢**。
- **硬编**：用显卡里专门的电路干活。好处是**快、省 CPU**；坏处是**质量差点**（同样的码率画质不如软编，想达到同样画质得加码率）、**功能受限**（不支持所有功能）。

打个比方：软编是"米其林大厨亲自做菜"（好吃但慢、贵）；硬编是"预制菜流水线"（快、便宜，但味道一般）。

## 3.2 软编 H.264 的两个旋钮：preset 和 tune

先讲清楚一个概念：**H.264 编码的参数非常多、非常复杂**，普通人根本调不完。所以 x264（FFmpeg 软编 H.264 用的开源库）干脆给你**预设了几套现成的方案**，你选一个档位就行，不用管细节。这两个旋钮就是：

### preset（预设档位）——"速度 vs 质量"的平衡杆

从快到慢有 10 档：

```
ultrafast → superfast → veryfast → faster → fast → medium → slow → slower → veryslow → placebo
（极快）                                            （默认）                              （超慢）
```

- 往左（ultrafast）：编得快，但文件大、画质差。
- 往右（veryslow/placebo）：编得极慢，但文件小、画质好。

**为什么会这样？** 因为压缩本质是"用计算时间换文件大小"。PDF 里扒了源码，你可以看到每一档具体在做啥，但你不必记源码，记住规律就行：

- **参考帧越多** → 预测越准 → 文件越小 → 但越慢。
- **B 帧越多** → 压缩越好 → 但越慢（要等前后帧）。
- **运动搜索算法越复杂** → 找运动找得越准 → 越慢。
- **亚像素精度越高** → 画质越好 → 越慢。

一句话：**在 preset 上，你就是在"快"和"省"之间选一个点**。实际工程一般用 `medium`~`veryfast` 之间，极少用 placebo（那是压终极画质用的）。

### tune（微调）——"针对内容类型"的小开关

preset 定完大方向，tune 是**针对视频内容再微调一下**：

- `film`：真人电影
- `animation`：动画（线条、平涂色多，有专门优化）
- `grain`：要保留胶片颗粒感
- `zerolatency`：零延迟（视频会议、直播推流用，不让你等）
- `fastdecode`：让解码更省事

**注意**：tune 只有在内容匹配时才用，不匹配反而有害。比如你压动画却选了 film，可能更差。

### profile（档次）——"功能套餐"

H.264 有几种套餐：baseline（最简）、main（主流）、high（高级）。档次越高，能用的高级功能越多，压缩越好，但**解码器也得支持**。大多数场景用 `main` 或 `high` 就够了。

## 3.3 ⚠️ 重点纠错：这些是 x264 的参数，NVENC 完全不是这么回事！

PDF 这一章有个**大坑**：它把 x264 的 preset/tune 讲完了，然后范例却叫"libx264_nvenc"，好像 NVENC 也吃这套参数——**这是错的**，你千万别照抄。

NVENC 是**显卡里的一块固定电路**，它没有 x264 那些软件算法，所以它的参数体系完全不一样。**在你现在用的 FFmpeg 8/9 里**，NVENC 的正确用法是：

- **preset 用 `p1`~`p7`**（不是 veryfast/medium 那些）：
  - `-preset p1`：最快，画质最差
  - `-preset p7`：最慢，画质最好
- **码率控制用 `-rc`**：`-rc vbr`（可变码率）、`-rc cbr`（恒定码率）、`-rc cqp`（固定质量）
- **质量用 `-cq` 控制**（类似 x264 的 CRF，数值越小质量越高）
- **tune 用 `-tuning`**：`hq`（高质量）/ `ll`（低延迟）/ `ull`（超低延迟）/ `lossless`（无损）

正确示范：

```
# 高质量、画质优先
ffmpeg -i in.mp4 -c:v h264_nvenc -preset p6 -tuning hq -rc vbr -cq 23 -b:v 0 out.mp4

# 直播推流、低延迟
ffmpeg -i in.mp4 -c:v h264_nvenc -preset p3 -tuning ll -rc cbr -b:v 4M out.mp4
```

**绝对不要再写 `-preset veryfast` 或 `-preset default` 这种给 NVENC 用**（`default` 是老接口的遗留值，新版已经废弃）。

# PDF 四：FFmpeg 硬件解码（CUDA / DXVA2 / D3D11VA / QSV）

## 4.1 什么叫"硬件解码"？

前面讲了硬编。解码同理：

- **软解**：CPU 一帧一帧地算，把压缩的视频还原成画面。兼容性最好。
- **硬解**：交给显卡里的专用解码电路。CPU 几乎不干活，速度快，尤其适合 4K/8K 和同时开很多路视频。

## 4.2 各家的"方言"——为什么有这么多名词？

问题来了：**每家的显卡都不一样**，解码电路也不一样。所以每个平台都有自己的"方言"（API）。PDF 里一堆名词，我用一张表给你翻译成人话：

| 名词         | 是谁的   | 在哪用    | 人话                                       |
| ------------ | -------- | --------- | ------------------------------------------ |
| DXVA2        | 微软     | Windows   | 老一代的解码接口                           |
| D3D11VA      | 微软     | Windows   | 新一代接口，**A/N/I 三家显卡都认它**，推荐 |
| D3D12VA      | 微软     | Windows   | 再新一代，FFmpeg 7.0 开始支持              |
| VAAPI        | Intel 等 | Linux     | Linux 上通用的解码接口                     |
| VDPAU        | NVIDIA   | Linux     | NVIDIA 在 Linux 的老接口                   |
| VideoToolbox | 苹果     | macOS/iOS | 苹果家的接口                               |
| CUDA / NVDEC | NVIDIA   | Win/Linux | NVIDIA 家的硬解/硬编                       |
| MediaCodec   | 谷歌     | Android   | 安卓手机上的接口                           |
| QSV          | Intel    | Win/Linux | Intel 核显的硬编硬解                       |

你不用全背，你只需要知道：**"选哪个接口"取决于你在什么系统、什么显卡**。

## 4.3 FFmpeg 的两条硬解路线（重要）

FFmpeg 给了你两种用硬件解码的方式：

**方式 A：`-hwaccel`（内部硬件加速）——推荐**

```
ffmpeg -hwaccel d3d11va -i input.mp4 output.mp4
```

特点：还是用软件解码器，但它会**自动检测**：如果能用硬件解，就悄悄转给硬件；**如果硬件不支持（比如特殊档位），就自动退回软件解码**。很安全，推荐日常用。

**方式 B：`-c:v` 指定硬解器——不推荐**

```
ffmpeg -c:v h264_cuvid -i input.mp4 output.mp4
```

特点：直接点名"必须用 `h264_cuvid` 这个硬解器"。**不支持就报错，不会退回软解**。一般不推荐，除非你明确知道自己要什么。

## 4.4 ⚠️ 两个过时点（PDF 里这么写，但现在已经变了）

1. **`cuvid` 系列（h264_cuvid 等）已经边缘化**。现在 NVIDIA 官方和 FFmpeg 都推荐用 `-hwaccel cuda` 或 `-hwaccel nvdec` 这种新方式，而不是点名 `h264_cuvid`。老的 cuvid 和新式 cuda 加速配合还会有已知问题。
2. **Intel 的 libmfx（Media SDK）已经废弃**，被 **oneVPL** 取代了。FFmpeg 6.0 起 QSV 已经用 oneVPL，你不需要再单独装老 SDK。

## 4.5 写代码时怎么用硬解？（C++ 步骤）

如果你自己在 C++ 里写解码程序，流程大概是（这是 FFmpeg 的标准硬解套路）：

1. **用名字找解码器**：`avcodec_find_decoder_by_name("h264_cuvid")`（或者不点名，用 `av_hwdevice_find_type_by_name` 找设备类型）。
2. **创建设备**：`av_hwdevice_ctx_create(...)`——相当于"打开显卡的大门"。
3. **告诉解码器"我要硬解输出"**：设置 `get_format` 回调，让解码器把帧直接解到显存里（输出 `AV_PIX_FMT_D3D11` 这种硬件帧格式）。
4. **正常解**：`avcodec_send_packet` / `avcodec_receive_frame`，和软解一模一样。
5. **取数据**：解出来的帧在**显存**里，如果要做软渲染或软件滤镜，用 `av_hwframe_transfer_data` 把它**拷回内存**。这一步就是"从显卡搬数据到 CPU"，比较费时，所以全硬转码时尽量别拷。

# 最后：给你画一张"这几份 PDF 到底在讲什么"的总地图

把你现在脑子里应该有的画面串起来：

1. **视频压缩** = 尽量少记东西：切块 + 猜（帧内/帧间预测）+ 只记猜错的残差 + 扔掉不重要的细节（量化）+ 最后再压一遍（熵编码）+ 磨平接缝（滤波）。
2. **H.265 vs H.264** = 块切得更灵活 + 预测方向更多 + 运动补偿更准 + 只用一个更高效的熵编码 → **省一半码率，但编码更费算力**。
3. **码流（.h265 文件）** = 一节一节的车厢（NALU），车厢=开始码+头部+数据。头部里的"类型"字段告诉解码器这是说明书（VPS/SPS/PPS）还是图像（IDR/P/B）。
4. **VPS/SPS/PPS** = 三份由大到小的说明书。
5. **I 帧的 19/20/21** = 19 和 20 是"安全关键帧"，21（CRA）是"省码率但有兼容风险的关键帧"，所以软编建议关 open-gop。
6. **preset/tune/profile** = x264 软编的"快慢旋钮 / 内容微调 / 功能套餐"。
7. **NVENC** = 显卡硬编，**参数体系和 x264 完全不同**，用 `p1~p7`、`-rc`、`-cq`、`-tuning`。
8. **硬件解码** = 用 `-hwaccel`（自动回退，推荐），选接口取决于平台（Windows 用 d3d11va，Linux 用 vaapi，Mac 用 videotoolbox，NVIDIA 用 cuda）。
